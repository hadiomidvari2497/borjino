**تاریخ ممیزی:** 2026-09-18  
**مرجع عملکرد:** `docs/PROJECT-SPEC.md`  
**مرجع UI/UX:** Nextable RTL  
**وضعیت:** Baseline Audit — پیش از ادامه توسعه

## 1. جمع‌بندی

ممیزی فعلی نشان می‌دهد هسته اولیه CRUD برای ساختمان، بلوک، واحد، اشخاص، قرارداد و شارژ وجود دارد، اما پروژه هنوز با سند مرجع جامع هم‌سطح نیست.

دو اصل اجرایی از این پس ثابت هستند:

1. UI/UX باید از الگوها و HTML واقعی Nextable پیروی کند.
2. عملکرد، داده و Business Logic باید دقیقاً مطابق `PROJECT-SPEC.md` باشد.

## 2. Authentication و Authorization

### موجود
- Session login
- `password_hash/password_verify`
- CSRF
- `require_login()`
- Logout

### شکاف
- جدول کاربران فقط اطلاعات پایه دارد.
- Access Group وجود ندارد.
- Permission صفحه‌ای وجود ندارد.
- Backend permission check برای CRUDها وجود ندارد.
- کاربر `admin` و گروه `administrators` با قوانین غیرقابل حذف/تغییر در دیتابیس مدل نشده‌اند.

### اقدام
ابتدا مدل User/Group/Permission پیاده‌سازی شود و سپس همه صفحات مدیریتی به Permission Check متصل شوند.

## 3. Buildings

### موجود
- نام، کد پستی، نوع، تاریخ ساخت، پارکینگ، انبار، استان، شهر، آدرس
- مدیر و تلفن مدیر در پیاده‌سازی فعلی وجود دارد.
- ویرایش
- جلوگیری از حذف در صورت وجود بلوک

### شکاف
- هزینه‌های ثابت ساختمان در مدل داده و UI وجود ندارد.
- حذف با GET انجام می‌شود و باید به عملیات POST/CSRF تبدیل شود.

## 4. Blocks

### موجود
- ساختمان
- شماره بلوک
- نام
- تعداد طبقات
- جلوگیری از حذف در صورت وجود واحد

### شکاف
- هر ساختمان «حداقل یک بلوک» باید در منطق ثبت/اعتبارسنجی سیستم کنترل شود.
- تغییر ساختمان بلوک در حالتی که واحد وابسته دارد باید بررسی کسب‌وکاری شود.
- حذف با GET باید اصلاح شود.

## 5. Units

### موجود
- سه روش ایجاد:
  - گروهی در سطح بلوک
  - گروهی در سطح طبقه
  - تکی
- کنترل تعداد طبقات بلوک
- متراژ
- پارکینگ/انبار
- وضعیت عملیاتی و مالی
- جلوگیری از حذف واحد دارای membership

### شکاف‌های مهم
1. سند مرجع وضعیت‌های عملیاتی را «خالی، در حال تعمیر، اجاره‌داده‌شده، فروخته‌شده» تعریف می‌کند؛ کد فعلی یک وضعیت اضافی `occupied` دارد. این اختلاف باید حذف/تصمیم‌گیری شود.
2. در فرم تکی، فیلدهای مشترک و بعضی فیلدها از include مشترک می‌آیند و باید UI نهایی یک‌بار و بدون تکرار نمایش دهد.
3. شماره‌گذاری گروهی در سند با «پیش‌شماره واحد» توصیف شده، اما پیاده‌سازی فعلی عملاً «شماره شروع» عددی دارد. این باید دقیقاً به رفتار تعریف‌شده تبدیل شود.
4. صفحه جزئیات مستقل واحد وجود ندارد.
5. محدودیت حذف فقط در UI/کد صفحه اعمال شده و باید با طراحی FK/Business Rule سازگار شود.

## 6. Personnel

این ماژول در نسخه فعلی وجود ندارد.

لازم است موجودیت مستقل Personnel با نقش‌های زیر ساخته شود:
- مالک ساختمان
- مدیر ساختمان
- حراست
- نظافت
- تعمیرات

هم شخص حقیقی و هم حقوقی باید پشتیبانی شود و هر نقش بتواند چند نفر داشته باشد.

## 7. Members

جدول `memberships` وجود دارد، اما UI و CRUD برای آن وجود ندارد.

لازم است:
- شخص به‌عنوان Member قابل ثبت باشد.
- رابطه Member ↔ Unit مدیریت شود.
- نقش‌های مالک/مستأجر/ساکن و اطلاعات مرتبط مدیریت شوند.
- حذف Unit دارای Member ممنوع بماند.

## 8. Contracts

### موجود
- Unit
- Person
- نوع rent/sale
- تاریخ شروع/پایان
- مبلغ
- ودیعه
- توضیحات

### شکاف
- ویرایش قرارداد وجود ندارد.
- فیلدهای قرارداد فروش به‌صورت مشخص و جداگانه مدل نشده‌اند.
- فرم باید بر اساس نوع قرارداد فیلدهای مرتبط را نمایش دهد.
- ارتباط قرارداد با وضعیت واحد و عضویت باید مطابق نیازمندی مدیریت شود.

## 9. Costs

ماژول هزینه‌ها در نسخه فعلی وجود ندارد.

باید شامل:
- هزینه‌های ثابت
- هزینه‌های متغیر
- قبض‌های مشاع
- تعمیرات
- هزینه‌های پیش‌بینی‌نشده
- معیار تخصیص هزینه: مساوی/متراژ/نفر/ترکیبی

باشد.

## 10. Charges

پیاده‌سازی فعلی فقط امکان ثبت مبلغ دستی برای یک Unit را دارد.

اما سند مرجع 10 روش محاسبه تعریف کرده است:
1. واحدی
2. متراژی
3. نفری
4. نفر-متراژی
5. واحدی + متراژی
6. واحدی + نفری
7. واحدی + نفر-متراژی
8. نفری + متراژی
9. واحدی + متراژی + نفری
10. هزینه‌محور

همچنین U، rm، rn، نسبت نفر/متراژ، هزینه‌های ثابت/متغیر، تاریخ صدور و قوانین هشدار باید قابل تنظیم باشند.

## 11. Payments

جدول `payments` وجود دارد ولی ماژول UI/منطق ندارد.

باید:
- ثبت پرداخت
- ارتباط با Charge
- مبلغ
- تاریخ
- روش پرداخت
- شماره مرجع
- وضعیت paid/partial/unpaid
- گزارش پرداخت

پیاده شود.

## 12. Users / Access Groups

در حال حاضر فقط جدول Users و login/setup admin وجود دارد.

نیازمند:
- CRUD کاربران
- گروه‌های دسترسی
- Permissionهای صفحه‌ای
- گروه immutable `administrators`
- کاربر immutable `admin`
- عدم امکان تغییر گروه admin
- اعمال Permission در Backend

## 13. Settings / SMS / Notifications

در نسخه فعلی وجود ندارد.

نیازمند:
- تاریخ صدور شارژ
- تعداد روز هشدار
- شماره اضطراری
- تنظیمات پنل پیامک
- تنظیمات عمومی
- هشدار نقص داده قبل از صدور شارژ
- گیرندگان: مالک، مدیر، شماره اضطراری

## 14. Reports

گزارش‌های زیر هنوز ساخته نشده‌اند:
- وضعیت واحدها
- بدهی/بستانکاری
- قراردادهای اجاره/فروش
- شارژهای صادرشده و وضعیت پرداخت
- فعالیت کاربران

## 15. Dashboard

Dashboard فعلی تعداد ساختمان/بلوک/واحد/شخص/قرارداد را نشان می‌دهد.

برای تطبیق با سند باید شاخص‌های برجینو اضافه شوند:
- واحدهای خالی
- اجاره‌ای
- فروخته‌شده
- در حال تعمیر
- مجموع بدهی
- مجموع بستانکاری
- شارژ صادرشده
- وضعیت پرداخت
- قراردادهای فعال
- اعلان‌های مهم

## 16. Nextable UI/UX

Shell فعلی از کلاس‌ها و ساختار Nextable استفاده می‌کند، اما چند نکته باید قبل از اعلام «مطابقت دقیق» اصلاح شود:

- Assetها از یک URL خارجی در زمان اجرا خوانده می‌شوند.
- منوی فعلی ساده‌شده است و هنوز تمام ماژول‌های برجینو را پوشش نمی‌دهد.
- صفحات داخلی هنوز به‌صورت کامل با الگوهای واقعی صفحات Nextable تطبیق داده نشده‌اند.
- فرم‌ها و جدول‌ها از کلاس‌های Nextable استفاده می‌کنند، ولی باید صفحه‌به‌صفحه با منبع HTML مرجع بررسی شوند.
- Login نیز باید با صفحه مرجع Nextable تطبیق داده شود، بدون اضافه کردن قابلیت‌هایی که در مشخصات برجینو نیامده‌اند.

بنابراین وضعیت UI فعلی «Nextable-based» است، نه هنوز «Verified Exact Match».

## 18. Definition of Done

یک ماژول زمانی «تمام‌شده» محسوب می‌شود که:

- Functionality مطابق PROJECT-SPEC باشد.
- CRUD کامل و اعتبارسنجی سمت سرور داشته باشد.
- Permission سمت Backend اعمال شود.
- قوانین حذف/ویرایش رعایت شود.
- UI با الگوی واقعی Nextable ساخته شده باشد.
- داده Demo قالب وارد منطق برجینو نشده باشد.
- خطاهای رایج ورودی مدیریت شوند.
- عملیات حساس CSRF داشته باشند.
- وضعیت موفق/خطا به کاربر نمایش داده شود.

## 19. تصمیم این ممیزی

در این مرحله **هیچ اختلاف عملکردی با حدس و گمان حل نمی‌شود**. مواردی که در سند مرجع صریح هستند مستقیماً پیاده می‌شوند؛ مواردی که سند درباره آن‌ها تصمیم صریح ندارد، قبل از تبدیل شدن به Business Rule جدید باید مشخص شوند.

**اولین کار اجرایی بعد از این Baseline:** تکمیل هسته Users + Access Groups + Permissions و سپس اتصال آن به تمام صفحات موجود.
